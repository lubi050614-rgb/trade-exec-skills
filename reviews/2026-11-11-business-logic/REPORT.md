### R01 — 通过持久化事件恢复成交，不能猜测 fill ID

**依据**：原规范第 4、6、17 节要求独立 Atomic 可调用，可靠成交先于记账，存在半完成步骤不得返回闭环成功。

**复现**：先用可信 fixture provider 发布行情，再通过 `execution-fill-record` / `cta-fill-record` 登记合法唯一 ID `adapter-trade-001`，暂不推进订单与记账。该笔成交已经消费本 bar 全部可用容量。随后调用对应 Upper 模拟工具恢复同一事件。

**实际**：两个 Upper 都按 `event_id + ':' + order_id` 查找成交，而非检索已经存在的记录。找不到自造 ID 后，容量已耗尽，新的 match 返回 0；循环结束，将事件标记 done，返回 `commit_status=COMMITTED`，但 `adapter-trade-001.accounting_status` 仍为 `ACCOUNTING_PENDING`。账户仍保留成交前状态。同一事件后续重试返回缓存“完成”结果。

**影响**：合法 Atomic 流程与 Upper 混合调用时不能可靠恢复，Agent 可被完成标志误导。资金没有因此重复入账，但成交事实未完成记账。

**修复方向**：以持久化事件/订单关联检索全部成交，不对 fill ID 命名做业务假设；提交最终成功前核验相关成交状态、释放状态和资源对账；将原事件缓存成功的条件收紧。

**证据**：`test_upper_recovers_arbitrary_persisted_fill_ids`；observations.json 中 `stock_external_fill_recovery` 和 `cta_external_fill_recovery`。

### R02 — 新目标生效后必须阻止旧目标腿提交

**依据**：新文档案例 D 明确要求用户改变目标后按新目标规划，不能盲目执行旧开空腿。

**复现**：v1 计划从多 3 转空 2，先完成平 3 并入账；此时创建同 target_id 的 v2 空仓目标（target_net_lots=0），成功返回空腿计划。再带最新账户版本提交 v1 的卖开 2 腿。

**实际**：提交成功，订单 NEW 并冻结资源。`check_order` 只检查该旧腿所属旧 plan 的目标数量；系统没有“当前有效目标版本”约束。当没有活动挂单时，现有挂单版本冲突检查也不会生效。

**修复方向**：持久化账户/合约/目标的生效版本；新目标接受时显式废止未提交旧腿或标为 superseded。提交必须检查腿仍属于当前目标。仅检查当前数量和账户版本不足以解决此问题。

**证据**：`test_cta_new_target_invalidates_old_opening_leg`；`stale_cta_target`。

### R03 — 同一股票目标版本会从 1000 股漂移到 900 股

**依据**：原规范 3.2：目标股数在计划生成时固定；重新调仓必须新建目标版本。

**复现**：净资产 100000、当前 400 股、参考价 10、目标权重 0.1。v1 计划目标 1000 股，新增买 600；全部成交并扣订单总费用 5 后，资产为 99995、实际持仓为 1000。用最新一致账户快照和相同 target/version、目标权重再次调用计划。

**实际**：函数重新计算 `floor(99995 × 0.1 / 10 / 100) × 100 = 900`，生成卖 100 股草稿，尽管原 v1 目标已经实现。

**修复方向**：保存目标版本对应的归一化结果和来源快照；同版本复用冻结数量。若调用被解释为改变原目标输入，应明确拒绝版本冲突并要求新版本，而不是静默生成反向单。需要同步明确 order-plan 的持久化/幂等契约。

**证据**：`test_stock_target_quantity_stays_fixed_for_same_version`；`stock_target_drift`。

### R04 — pending 登记可绕过股票方向/目标版本冲突

**依据**：原规范 3.3、4、6：不同目标版本或反向活动订单应报 OPEN_ORDER_CONFLICT，写 Atomic 不得绕过提交前置条件。

**复现**：在同一个账户版本上独立登记 BUY 100 / v1 和 SELL 100 / v2。登记时两者均为 PENDING_RESERVATION，因此登记阶段的活动订单冲突检查均通过。先预留 BUY，再读取新账户版本预留 SELL。

**实际**：两笔订单均变成 NEW。reserve 只再次检查规则、时间和可用资源，没有重跑登记时的活动订单冲突检查。

**修复方向**：将激活订单所需的完整检查抽为共享函数，在 reserve 的同一事务内基于当前状态重验。不要只依赖 register 的旧检查结果。

**证据**：`test_stock_atomic_reservation_rechecks_open_order_conflicts`；`stock_reserve_conflict`。

### R05 — 当前同步撤单模型不能验收异步撤单竞态

**依据**：新文档 A09/A11/G02/G03/G06/G10 和案例 A；原规范 3.3 也明确尚未确认的撤单余量仍计入在途。

**复现**：A1 买 1000 股，A2 已成交 400@9.90，此时现金 16040、冻结 6000。将 A3“仅发出撤单申请”交给现有唯一撤单入口。

**实际**：立即置 CANCELED 并释放冻结至 0，而 A3 期望冻结仍为 6000、累计成交仍 400、cancel_pending=true。工具没有申请/确认/拒绝的事件区分，不能继续表达 A4 的交叉成交和 A5 的最终确认。

**边界说明**：原实现可被解释为本地撮合器同步确认撤单，这不等于已经实现错误的实盘撤单 API；它是新逐事件验收明确暴露的能力缺口。测试是在检验它能否承载 A3，不是假定当前同步工具已经承诺异步语义。

**修复方向**：保留原订单成交状态，单独记录 cancel_pending；在有效撤单确认及成交明细对齐后释放。提供可测试的 request/ack/reject 与交叉成交调度，未必需要增加顶层工具数量，但需扩展事件契约。

**证据**：`test_case_A_cancel_request_must_not_release_before_confirmation`；`A3_cancel_request`。

### R06 — FILL_CONFLICT 没有形成持久化对账状态

**依据**：新文档 G05、E″：冲突必须保留记录、进入 RECONCILE 并阻止相关新增风险。

**复现**：先登记并记账一个合法 fill；再使用同一 fill_id 提交不同事件来源。当前接口不能直接传入成交价/量，因此用它已经支持识别的 payload 冲突来验证后续状态处理。

**实际**：返回 FILL_CONFLICT，但异常处理回滚全部状态，冲突前后持久化会话完全相同；没有冲突审计记录或待对账标志。随后用最新账户版本提交新的买单仍然成功。

**修复方向**：分开“拒绝改变已确认账务”和“可靠保存冲突事实”；持久化冲突及账户/订单对账状态，新增风险检查读取该状态；查询、既有有效成交记账和权威对账恢复需有独立路径。

**证据**：股票路径实际复现 `test_conflicting_fill_requires_persistent_reconciliation` / `conflict_not_latched`。CTA 具有同样的异常回滚与未持久化冲突结构，本轮该项未另做 CTA 动态复现，不能算作双路径动态证明。

### R07 — 股票零股卖出不能忽略费用不足

**依据**：原规范资金/费用检查和非负可用约束；新文档 G01，且第 5.3 节明确还需补卖单冻结/费用边界案例。

**复现**：额外合成边界 fixture，现金 0、可卖尾仓 1 股、卖价 1、订单总费用固定 5；数量/价格在该测试 profile 内合法。这不是将案例 A/B 的 9–11 价格范围改称真实规则。

**实际**：提交成功，冻结可卖 1 股，预留现金 0。之后模拟成交在记账阶段才报 INSUFFICIENT_CASH 并回滚；订单仍 NEW。没有实际产生负余额，但系统已经受理一个资金不足以结算的订单。

**原因**：resource-check 对 SELL 永远将 required_cash 设为 0，费用仅返回、不参与资源需要计算。

**修复方向**：按明确的卖出收入与费用抵扣策略，检查并原子预留必要差额；若采用费用全额预留，也应通过 profile 明确，提交、撮合和记账使用相同口径。

**证据**：`test_stock_sell_fee_shortfall_must_fail_before_reserving`；`sell_fee_shortfall`。

### R08 — D4 的冻结口径冲突需要版本化策略选择

**依据**：新文档案例 D4 固定：卖开 2@4000、乘数 10、保证金率 10%、费用 10，冻结保证金 8000、合计冻结 8010、可用 91975。

**复现条件**：合法合成价格范围设为 3600–4400，实际成交/mark 均为 4000。其他参数逐项按案例 D。

**实际**：现有代码固定对 SELL 使用 profile.upper_price=4400 作为预留价，冻结 8800+10=8810，可用 91175，多冻结 800。D1–D3 与 D5 的余额结果吻合，D5 最终权益 99975 和可用 91975 正确；差异出现在 D4 冻结阶段。

**边界说明**：上限冻结是已经说明的保守策略，可防止卖单在更高价格成交时保证金被低估，不能简单定性为保证金计算公式错误。本问题是 test-v1 与当前策略没有显式区分。

**修复方向**：确认按委托价还是独立保护上限冻结，形成 reservation policy/version；测试 oracle 必须对应所选 profile。若支持按委托价冻结，需要同时定义更高成交价导致保证金不足时的处理，不能仅为通过数字测试删除资金保护。

**证据**：`test_case_D_reversal_reservation_matches_test_v1`；`D1_D5`。

## 五类案例的覆盖结论

| 案例 | 结论 | 说明 |
|---|---|---|
| A 部分成交与撤单竞态 | 不满足新增事件验收 | A1/A2 金额正确；A3–A5 缺申请/确认分离，不能宣称完整通过 |
| B 资金临界点含费用 | 已验证通过本地投影 | 10000、10004.99 拒绝且不留订单；10005 可提交，全部成交后现金/冻结均 0，今日买入不可卖 |
| C 开仓、两日盯市与部分平仓 | 已验证通过本地投影 | C1–C6 的 B/U/E/M/合计冻结/可用逐项吻合，最终权益 100485；报表尚未分列 Fm/Ff |
| D 反手 | 部分通过，存在策略口径差异 | 平仓依赖和最终余额正确；D4 冻结偏离 800；另确认新目标不会阻断旧开仓腿 |
| E 重复成交与状态回报 | 部分通过 | 已登记 fill 的重复推进/入账不重复扣费，现金 18995；外部累计委托回报、E′ 等待明细状态无接口，E″ 未形成持久化对账 |

A/B/C/D/E 的回放事件是文档给定成交事实。当前工具只支持从完整 bar 合成成交，因此本轮明确使用等价合成 bar 验证能够映射的账务步骤，没有将其称为对任意柜台成交回报的完整回放。价格未改变 oracle，时间按合法模拟 bar 边界展开。

## 决策表补充覆盖范围

详见 `decision-coverage.md`。以下是当前不能据已有 42 组测试宣称已覆盖的能力：

- 原始委托/成交/撤单回报及规范化唯一键、raw_status、映射版本；累积状态先到时的 FILLED_AWAITING_TRADES。
- 9:20–9:25、14:57–15:00 的撤单阶段约束，以及撤单拒绝或不确定送达后的对账。
- 价格笼子基准、数量上限、独立卖出最小量；现有合成 profile 的标记不能替代这些条件。
- 客户级权限/禁止新增风险/交割回避状态、费用与保证金参数有效期、规则未来施行与暂缓事项。
- 跨策略共享生产账户的资源权威来源、真实账户/柜台版本映射。当前 mock 会话隔离是已有范围边界，本轮未误报为生产集成已经存在。

5. R08：先冻结 test-v1 与保守冻结策略的适用边界，再扩展规则/风险 profile。
